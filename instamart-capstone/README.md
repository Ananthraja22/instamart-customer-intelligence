# Instamart Customer Support and Analytics Capstone

This project uses the assignment's fictional synthetic dataset to demonstrate
data preparation and EDA, customer segmentation and churn-risk analysis,
guarded ticket classification, and a policy RAG support copilot.

It does not contain actual Swiggy Instamart data and does not connect to live
systems, contact customers, or issue refunds.

## Problem and approach

The project turns synthetic customer, order, product, ticket, and policy files
into a reproducible support analytics workflow:

1. Normalize and validate records, identify duplicate order snapshots and
   numeric outliers, and load clean tables into SQLite.
2. Explore customer and order patterns with saved charts and SQL reports.
3. Build RFM customer segments using standardized K-Means and choose K by
   comparing inertia and silhouette scores for K=2 through K=8.
4. Derive a transparent cluster-based churn-risk flag from RFM profiles. This
   is unsupervised segment risk, not a trained churn probability.
   The saved model can also assign segments and relative risk flags to new
   customers from an input CSV with `recency_days`, `frequency`, and `monetary`.
5. Triage support tickets with blank-text, length, and sensitive-data guards;
   offer local rules, zero-shot, and few-shot modes.
6. Retrieve policy chunks for grounded support answers and run refund checks
   against the synthetic order table.

## Data cleaning and validation rules

- **Customers:** trim IDs; map case and spelling variants of the six supported
  cities (including Bangalore/Bengaluru, Bombay/Mumbai, Madras/Chennai, and
  New Delhi/Delhi); map gender variants to Male, Female, or Unknown; coerce
  invalid dates and numeric ages; impute missing ages with the dataset median;
  retain the first record for duplicate customer IDs.
- **Products:** trim text and IDs, coerce price to numeric, drop records missing
  product ID or price and non-positive prices, and keep the first record for a
  duplicate product ID.
- **Orders:** coerce timestamps and numeric fields, remove rows missing required
  keys/time/quantity/order amount, remove exact duplicate snapshots, then keep
  the latest status snapshot for each order ID while preserving its earliest
  timestamp as the order time. The cleaner stops if one order ID has multiple
  product IDs. Missing delivery time is allowed for non-delivered orders.
- **Tickets:** trim identifiers and text, keep the first row for a duplicate
  ticket ID, and preserve blank text so Part C can record and skip it.
- **Evaluation files:** remove incomplete rows and exact duplicate rows.
- **Outliers:** report IQR bounds and individual flagged records for age,
  quantity, order amount, and delivery time. IQR uses the 1.5×IQR rule. Flagged
  values are retained unless they violate an explicit validity rule; a large
  legitimate order amount is not silently discarded.
- **Validation:** check required row/column minimums, unique entity keys,
  standardized city/gender values, numeric ranges, Pandas foreign keys, SQLite
  row counts, and SQL anti-join orphan counts.

The raw CSV files are not modified. The source dataset has 1,200 customers
(five columns) and more than 500 rows, so it meets Part A's minimum.

## Run data preparation, analysis, and K-Means

    .\run_pipeline.cmd

The runner executes:

1. Raw-data audit.
2. Cleaning and standardization.
3. EDA, IQR outlier reports, and SVG visualizations.
4. SQLite database build.
5. Pandas and SQL validation.
6. SQL analysis.
7. RFM K-Means evaluation for K=2..8, customer segments, and cluster-based
   churn-risk outputs.
8. Default guarded rule-based ticket triage.
9. Refund-scenario evaluation.
10. Policy chunk retrieval evaluation.

Useful outputs include outputs/kmeans_k_evaluation.csv,
outputs/kmeans_inertia.svg, outputs/kmeans_silhouette.svg,
outputs/customer_segments.csv, outputs/churn_risk_predictions.csv,
outputs/identified_outlier_rows.csv, and the other SVG charts.

### Predict segments for new customers

Run the pipeline first to create `state/customer_rfm_kmeans.joblib`. Prepare a
CSV with one row per customer and these numeric columns: `recency_days`
(nonnegative days since the last completed order), `frequency` (nonnegative
completed order count), and `monetary` (total completed-order value). Any other
input columns, such as `customer_id`, are preserved in the results.

    python scripts/modeling/predict_customers.py --input path/to/new_customer_rfm.csv

The default output is `path/to/new_customer_rfm_predictions.csv`. Use
`--output path/to/results.csv` to choose another destination. Customers with
zero frequency are labeled `No completed orders`; other rows are assigned to a
cluster using the saved scaler and K-Means model. `churn_risk` is a relative
cluster-based flag, not a trained churn probability or forecast.

## Part C: ticket guardrails and learning modes

The default pipeline uses local rules and does not call a language model. Before
classification the script:

- skips null, empty, and whitespace-only text;
- blocks prompts whose conservative UTF-8 byte upper bound exceeds the configured
  maximum (default 2,048);
- redacts email addresses, phone numbers, order IDs, and customer IDs;
- checks the complete prompt again and blocks it if a sensitive pattern remains;
- writes only ticket metadata and guardrail decisions, never raw ticket text or
  prompts.

Zero-shot and few-shot modes are available with a locally installed Ollama
model. They do not send ticket data to a hosted service:

    $env:OLLAMA_MODEL = "your-installed-local-model"
    python scripts/support/triage_tickets.py --mode zero-shot
    python scripts/support/triage_tickets.py --mode few-shot

The few-shot prompt uses four fictional, identifier-free examples. To lower the
prompt cap, set $env:MAX_PROMPT_TOKENS = "1024". The cap uses UTF-8 bytes as a
conservative token upper bound so an overlong ticket is blocked before the
model request.

## Part D: RAG API and React copilot

Policy text is split into fixed 80-word chunks with 16-word overlap. TF-IDF
retrieval selects relevant chunks and reports source filenames and chunk IDs.
If OLLAMA_MODEL is configured, the API uses a local Ollama model to generate
an answer grounded in those chunks; without it, the API returns the most
relevant chunk extractively.

Start the local API in one PowerShell window:

    python scripts/agent/rag_server.py

In another window, install and start the React UI:

    cd frontend
    npm install
    npm run dev

Open http://localhost:5173. The API is at http://127.0.0.1:8000, with a
machine-readable contract at /openapi.json. Refund queries can use the
separate synthetic customer and order ID fields; local code checks ownership,
completion status, delivery time, and the INR 1,000 escalation threshold. The
7-day request window cannot be checked because the data has no request date.
No real refund is issued.

The React app is the project's local support copilot. The REST/OpenAPI contract
is an integration point for a Copilot client; a Microsoft Copilot Studio
connection is not configured because no tenant or connector details were
provided.

## Findings and interpretation

The supplied cleaned snapshot contains 1,200 customers, 40 products, 12,197
canonical orders, and 164 tickets. City aliases resolve to six standard city
labels. Gender counts are 610 Female, 560 Male, and 30 Unknown.

The IQR report flags 5 customer ages, 983 order amounts, and 959 delivery
times; it flags no order quantities. These are review flags, not automatic
deletions. Large order amounts and delivery times can be valid synthetic
observations, so the cleaner only removes values that violate explicit data
rules.

K-Means tested every K from 2 through 8. Silhouette scores were 0.4654,
0.4441, 0.5240, 0.4761, 0.4819, 0.4170, and 0.3781 respectively; the best
score selected K=4. Inertia falls as K grows, so it is read alongside the
silhouette results rather than used alone. Cluster IDs are arbitrary; the
churn-risk flag is derived from relative cluster RFM profiles and is not a
calibrated churn probability.

Guarded rules triaged 164 ticket rows: 156 were classified, 4 blank tickets
were skipped, and 4 overlong tickets were blocked. Refund scenarios matched
7/7 expected outcomes. Policy retrieval matched the expected document and
found the expected fact for all 12 evaluation questions. These are evaluations
on the supplied synthetic scenarios, not guarantees on live customer data.

The order-status summary includes all final statuses. Sales by product category,
top-customer spend, and completed-sales charts include completed orders only.
The late-order amount is a potential refund pool before checking request timing
or human approval.
